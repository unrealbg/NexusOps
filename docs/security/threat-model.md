# Threat model

## Assets and trust boundaries

Protect SSH passwords, private keys/passphrases, trusted server identities and the user's remote machines. Treat the renderer, all host form inputs, DNS, remote SSH output, local files and dependency updates as separate trust boundaries. The application runs with the user's ordinary local privileges and the remote account's existing SSH privileges. NexusOps itself requests no elevation; a separately confirmed Windows installer launched by the OS may later present UAC outside the running process. Remote changes occur only through explicit terminal input or approved typed SFTP plans.

## Network attacker and first contact

russh verifies the actual negotiated host key before sending credentials. Pins bind canonical configured hostname and port, key algorithm and SHA-256 fingerprint. DNS changes do not bypass the configured endpoint's pin. Host aliases intentionally have separate pins. Unknown hosts fail the handshake and show hostname, port, algorithm and fingerprint for explicit trust. The service accepts only the current pending challenge. It reconnects and verifies again after trust, closing a key-change race between approval and connection.

TOFU cannot prove the identity of a first-contact endpoint under active attack. The user must compare the fingerprint through an independent trusted channel. Changed keys remain blocked before authentication and cannot be accepted through the first-contact API. Guided rotation uses the key observed in the blocked handshake and the currently persisted old pin, requires independent out-of-band verification, then changes only the local canonical endpoint pin through one-shot five-minute backend authority and exact compare-and-swap. No renderer-supplied fingerprint, generic override or automatic reconnect exists. Deleting a host configuration preserves endpoint pins; hosts sharing a canonical hostname and port share a rotated pin.

## SSH trust information view

Security reads endpoint pins as local persisted trust state, without any `SecretStore` access, new connection, remote command, pin mutation, audit event, or snapshot persistence. The configured authentication method is metadata only, not proof that a credential exists or works. The narrow getter validates stored host configuration and bounded pin values and fails with a fixed storage error on corruption; failure is never presented as Not pinned. Pins remain scoped to canonical hostname plus port, so delete/recreate can retain a pin while a different alias or port has separate state.

A displayed offline pin is not a fresh observation of the remote server. An active Connected session reached Connected only after the SSH transport verified the presented raw host key against the endpoint pin. `HostSession.identity` currently contains local pin metadata recorded after that successful verified connection; it is not an independently captured second handshake measurement. The UI claims verification at session establishment only for a matching Connected session with identity and session ID. Remote closure, missing/mismatched metadata, or session-query error removes that claim. Pin-read/refresh failure removes prior trust data. Existing session polling is reused; pin metadata has no background polling.

The rotation plan/execute path never opens SSH, authenticates, sends a remote command, accesses SecretStore or mutates a remote host. On success it clears the blocked session to Disconnected; a fresh ordinary connect must verify the new pin before authentication. Already established sessions are not retroactively reverified. The explicit checkbox aids human review but is not an integrity control against a compromised renderer. Rotation emits a High-risk metadata-only `identity.rotate` audit event, with no endpoint or fingerprints. Audit and pin stores are not atomic; if the audit append fails after the pin changes, the error is surfaced and a local Security refresh reveals the authoritative pin.

A malicious local account that can modify NexusOps profile storage can tamper with host/pin metadata, including syntactically valid values. Security is not an attestation of local OS integrity or a security/compliance score. See [SSH endpoint trust architecture](../architecture/security.md).

## Credential handling

`SecretStore` is the only persistence API for credentials. The production vault stores AES-256-GCM ciphertext in SQLite, with random nonces and authenticated revision identifiers. Windows Credential Manager, macOS Keychain or Linux Secret Service stores the vault key through keyring 4's platform-backed API. There is no plaintext fallback. Large private keys do not depend on the OS's per-secret blob limit. A locked or unavailable keychain fails with `secureStorage`.

Reading a missing master key never creates a replacement. A durable vault initialization marker also prevents automatic key creation during later writes, even after every credential has been deleted. Key loss requires deliberate recovery outside Goal 01. Ciphertext reads are bounded before loading SQLite blobs, including worst-case JSON escaping of otherwise valid credential inputs.

Credential input has no Debug or Serialize implementation. Rust owns zeroizing buffers for passwords, key PEM, passphrases, decrypted JSON and master keys. The SSH library needs transient copies and decrypted key structures; no promise is made that every allocator, crypto-library buffer, IPC buffer or OS copy can be wiped. JavaScript strings cannot be reliably zeroized. Form controls are cleared before awaiting IPC and on dismissal, and credentials bypass TanStack mutation caches. They never enter browser storage, Query snapshots, Zustand, logs, audit or plaintext configuration. Private keys are pasted into a transient form field; local file paths are not persisted.

Compromise of the logged-in account, debugger access, injected renderer code at runtime, a malicious OS/keychain or memory dumps can expose active secrets. Full-disk encryption, OS account security and dependency review remain important deployment controls. Copying the data directory alone is insufficient to decrypt secrets; losing the OS keychain key makes old credentials unrecoverable. Backups and migrations must account for the keychain; no credential export is provided.

## Remote-host and output safety

The IPC allowlist exposes no command, process, filesystem or shell plugin. Only bundled content in the main window receives custom command permissions; no remote URLs are granted IPC. CSP blocks external scripts, frames and network connections except Tauri IPC (and the loopback Vite server in development). React renders remote values as text.

The operation engine admits a fixed read-only enum, with no caller-supplied command strings. It does not source `/etc/os-release` or construct shell commands from host inputs. Live monitoring adds only constant reads of `/proc/stat` and `/proc/net/dev`, and reuses the fixed memory and root-filesystem reads. Monitoring IPC accepts exact host/session identities rather than paths or shell text; counter baselines are invalidated on session turnover. It bounds each probe execution by 8 seconds and combined stdout/stderr by 64 KiB; transport additionally bounds channel setup and cleanup. DNS/handshake is bounded to 15 seconds and authentication to 30 seconds. Cancellation and session lifetime guards tear down network I/O. Expensive encrypted-key decoding runs on a blocking worker; a started native KDF cannot be forcibly interrupted and may outlive a canceled request briefly.

Remote SSH servers may lie about data or be malicious. Output sizes, numeric ranges, invalid text and malformed records are checked, and optional failures remain warnings. A fixed command still executes through the remote account's shell and existing command environment; a compromised remote account may redefine utilities. NexusOps cannot guarantee that a hostile server implements those commands as read-only. Fixed discovery and monitoring operations request reads only; they do not install software, request sudo or modify services/firewalls. Separately, explicit terminal input can mutate the remote host, and approved typed SFTP plans, including remote editor saves, can create, replace, rename or delete remote files within their documented authority.

Services inventory uses one fixed read-only `systemctl --system ... --type=service --property=... show` operation for loaded service units. The renderer cannot supply command text or a unit name, and Services exposes no service mutation, sudo or journal capability. Parser bounds and display validation reject malformed or deceptive output; an untrusted host can still lie about service state. A successful empty response differs from an unavailable system manager. Snapshots remain component-local, session-bound, and are requested only on workspace entry or manual Refresh. See [Services architecture](../architecture/services.md).

Network inventory uses one fixed read-only `LC_ALL=C ip -j address show` operation. The renderer supplies only exact `HostId` and `HostSessionId`, never an interface, address, filter or command argument. No route, socket, DNS, firewall or interface-mutation surface is exposed. Interface names and IP addresses are untrusted topology metadata; selected fields are bounded and validated before renderer publication. A malicious SSH account can redefine `ip` or lie about kernel state, so this is observation rather than attestation. Snapshots remain component-local, session-bound and unpersisted; see [Network architecture](../architecture/network.md).

## System journal read boundary

Logs deliberately adds a sensitive read authority: up to ten newest accessible system journal records from the current boot, through one fixed `journalctl` command. Messages can contain credentials, personal data, URLs and arbitrary application payloads; display normalization is not secret redaction. Only `HostId` and the current `HostSessionId` cross the request boundary. No renderer-selected unit, filter, time range, boot, cursor, limit, path or command argument is allowed. No sudo, access/group/ACL change, package installation, remote file read, journal maintenance or mutation is added. Existing account permissions determine visibility; an empty success is not proof that the host has no logs.

The unchanged engine limits are eight seconds and 64 KiB, with the existing combined transport-output protection. Ten raw JSON-lines records are counted before projection. Malformed/overflowed snapshots fail closed. Required timestamp text is validated and converted to UTC; technical cursor/boot/monotonic fields never reach the renderer. MESSAGE null/binary/multi-value content is omitted, not stringified. Text is independently byte-bounded and dangerous controls are visibly escaped; oversized escaped text is omitted rather than silently truncated. Optional fields and priority are validated. React renders inert text without HTML, ANSI interpretation, links, Copy or Export. See [Logs architecture](../architecture/logs.md) for deterministic parser rules.

Independent admission and before/after session-generation checks reject stale or concurrent requests. Snapshots and local filters remain in the active component, cleared on disconnect/host/session replacement. No journal-specific polling, per-read audit, log content, Query/Zustand data, SQLite/history/browser persistence or new clipboard/filesystem permissions are introduced. Raw/parsed journal values, entry timestamps and search text must never appear in diagnostics, screenshots or published evidence. Transport buffers, parser/IPC data and active UI memory necessarily contain content; a compromised renderer, debugger, local account or memory dump can observe it. This is not a secure-erasure or hostile-server attestation guarantee.

## Docker system-daemon inventory boundary

Containers adds exactly one fixed read-only Docker list operation through `--host unix:///var/run/docker.sock`, requesting at most 64 recently created containers in all states and only ID, image, name, state, status, ports and networks. The renderer supplies only exact host/session identities, never an endpoint, context, command, container ID or filter. No Docker inspect/logs/stats, actions, mutation, API forwarding, Podman or remote context is exposed. NexusOps uses only Docker access already held by the authenticated SSH account. It does not use sudo, grant Docker access, alter group membership, change socket permissions or configure the daemon.

Access to a Docker daemon can itself convey powerful host-level authority; a read-only NexusOps list operation does not make that existing account privilege low-risk. The fixed command executes through the remote shell environment, where a hostile account can replace or redefine `docker`, and the result is observation, not attestation. Names, images, ports and networks may reveal sensitive infrastructure metadata. Strict JSON-lines bounds and display validation reject deceptive output before renderer publication; React renders inert text. Independent admission and exact session/generation checks prevent overlapping or stale publication. Snapshots and filters are component-local, with no polling, Query/Zustand/SQLite/browser persistence, metadata logging or per-read audit payload. See [Containers architecture](../architecture/containers.md).

## Interactive terminal boundary

An interactive PTY is an explicit user-controlled capability and is separate from structured operations. React receives seven dedicated terminal commands for list, open, poll, input, resize, local rename and close. It still has no generic command/process/filesystem API. Every operation validates `HostId`, the current `HostSessionId`, and `TerminalSessionId` in Rust. Reconnect always changes the connection identity, so a stale terminal ID cannot be used against a new transport or another host.

Terminal input is deliberately arbitrary and can mutate the remote system with the SSH account's privileges. NexusOps does not classify it as an operation, ask for structured-operation approval, retain local command history, or audit its content. The remote shell may retain history according to its own configuration. Users remain responsible for commands entered into the shell.

PTY output, input, search terms, selections and clipboard contents are potentially secret. Output stays in xterm's bounded in-memory scrollback and a bounded transport queue; no contents enter logs, audit, application state stores, databases, crash reports, screenshots by default, analytics or AI. Safe logs record identifiers and failure stage only. The renderer necessarily sees active PTY bytes, and explicit Copy/Paste necessarily accesses plain text in the system clipboard. Only clipboard read-text/write-text permissions are granted; image, HTML, clear and automatic clipboard access are absent.

The per-terminal Rust queue is capped at 64 chunks of 16 KiB and backpressures the SSH receive window. Poll responses are capped at 64 KiB, input calls at 16 KiB, xterm scrollback at 10,000 lines, active terminals at eight per host, and startup/I/O/close operations have deadlines. These controls limit accidental or hostile output growth but do not make an interactive remote shell harmless. Sustained output can still consume CPU, the remote can emit deceptive control sequences, and the user can paste dangerous commands.

Production still serves bundled assets under a restrictive CSP and freezes JavaScript prototypes. The xterm 6 bundle contains one namespace assignment that conflicts with a frozen inherited `toString`; a version-pinned build transform creates the same own property with `Object.defineProperty` and stops the build if the expected source construct changes. Remote terminal text is consumed by xterm rather than interpolated into HTML.

## SFTP and local file boundary

SFTP reuses the verified SSH transport on a separate subsystem channel. Per-host startup serialization prevents concurrent renderer calls from publishing and invalidating competing subsystems. The renderer has no local byte-payload command. Native selection creates an opaque typed grant in Rust, scoped to one host/connection/subsystem and revoked on disconnect or reconnect. An immutable backend plan binds it to exact endpoints, opened local handles, observed source/destination identities, a per-item destination action, risk, expiry, and one execution. Approval cancel/close discards named plans, and idle expiry tasks bound abandoned grants and plans. Consume/discard ownership is atomic, so cancellation cannot revoke an already active operation. The approved local path may be displayed to the user but is excluded from logs and published evidence. These checks limit confused-deputy and stale-session use; they cannot prove a human saw an honest prompt after renderer compromise.

Remote names are untrusted data. Operational POSIX names are distinct from escaped display names and Windows destinations. Server-returned traversal children, special-file transfers, Windows-invalid names, reparse destinations, and silent overwrite are rejected. New and replacement data is staged beside the target and the old target is preserved until a negotiated commit primitive succeeds. No shell fallback, recursive delete, executable preview, automatic open, general chmod/chown command, sudo, or remote hash command exists.

The remote server, local filesystem, or another writer can race metadata checks. SFTP v3 does not provide a universal compare-and-swap operation for replacement. NexusOps retains upload file and download directory/temp-file handles, rejects reparse ancestry, and revalidates identities before and after streaming where metadata permits. Windows identity is the volume serial plus full 128-bit file ID read from each open handle; Unix identity is device plus inode. Size and modified time are separate mutable preconditions. Unsupported strong identity fails closed. On Windows, upload handles deny write/delete sharing and the selected directory handle denies deletion. Terminal history drops all local handles before publishing its final state, and any new attempt needs a new picker grant. These guarantees still do not defend against a malicious logged-in account, administrator, filesystem driver, storage fault, or a remote server that changes bytes without changing the SFTP v3 size/mtime identity. No-clobber primitives, confirmed staging ownership, final revalidation, and destination serialization reduce accidental races. `OutcomeUnknown` is used when a lost reply prevents an honest result; generic retry rejects it.

Transfer memory is bounded by queue/history limits, per-host/global semaphores, directory caps, protocol packet ceilings, and 64 KiB payload chunks. File contents and transient operational paths are not logged or audited or persisted as transfer history. Goal 02C's bounded remote text is kept only in transient component-local renderer memory and the short-lived backend save authority, never in Query, Zustand or browser storage. A crash may leave a unique staging file; NexusOps never wildcard-deletes it after restart.

Remote text saves additionally compare bounded original-byte SHA-256 as well as SFTP v3 metadata before staging and replacement. This catches same-size edits within the one-second mtime resolution but is still not an atomic CAS against a writer racing after the final check. Editor replacement preserves and verifies available POSIX mode and uid/gid or fails closed. SFTP v3 does not expose ACLs, xattrs, SELinux labels, capabilities, hard-link relationships or filesystem-specific metadata, so files relying on them are outside the editor's safe scope. See [Remote text editor](../architecture/editor.md).

## Persistence, logs and audit

SQLite parameter binding prevents metadata SQL injection. Credential revisions avoid unsafe cross-store updates; crashes may leave encrypted orphans for future maintenance. Local profile locking prevents concurrent instances. Unix profile permissions are restricted to the owner; Windows uses the user's application-data ACL. A local attacker able to write the profile can alter host metadata or pins; pins are not a defense against account compromise.

Audit records contain identifiers and outcomes only, never credential values or output. Log diagnostic context uses stage, safe error codes and I/O kinds rather than full library error/config Debug. Audit rotation keeps two bounded files; logs keep seven daily files. Audit is not cryptographically tamper-evident. Audit write failures are surfaced even if a local action has already completed; refreshing host state resolves that partial-success situation.

The release bootstrap accepts an alternate test profile only through `NEXUSOPS_TEST_APP_DATA_DIR`, and only when the path is absolute and has the exact isolated-profile ownership marker. This prevents an accidental environment override from redirecting normal application data. It is not a sandbox against a malicious local account that already controls the process environment and filesystem.

Every renderer-callable custom command is admitted under one native process lifecycle mutex and retains a counted RAII permit until its complete invocation returns. Irreversible sealing rejects later commands with one safe error and drains admitted work for at most 60 seconds; timeout remains sealed. Normal exit then shuts down updates and application resources, revokes local picker grants, and finalizes the logging worker in a fixed asynchronous order. The Windows installer path uses a serialized exclusive seal: its permit remains alive while all other admitted work drains, and authority is consumed only after it becomes the sole permit. Failures do not reopen admission or trigger automatic retries. Source-policy tests fail if a custom command loses this boundary or a renderer lifecycle capability appears. This controls shutdown races within the process; it does not protect against a malicious local administrator, abrupt OS termination, power loss or injected code. See [process lifecycle](../architecture/lifecycle.md).

Ed25519 is the supported client-key type in the Windows alpha. Optional RSA support is disabled because the current upstream RSA implementation has an unfixed RustSec timing-side-channel advisory. Other parsed key formats are not claimed as verified support.

## Release supply-chain boundary

Goal 04B added development tooling and a manual GitHub Actions provenance candidate workflow. Goal 04C added a reviewable public updater key and a separate, manual version-bound signed-artifact workflow; its hosted signing acceptance passed on Windows, Linux and macOS. Goals 04D–04G added explicit manifest checking, bounded artifact download and verification, native process quiescence and one separately confirmed Windows-only installer authority. Goal 04I adds release-source identity, deterministic `latest.json`, exact target/assets and distinct owner-invoked draft and activation workflows. Exact SemVer comparisons fail on mismatched Cargo, Tauri, npm or lockfile versions. Required workflow inputs assert rather than choose clean source identity. Candidate run, source, public-key hash, platform, architecture, payload/signature hashes, trusted comments and cryptography are rebound before draft upload and again before activation. Full-SHA action pins reduce moving-ref risk; checkout does not retain its credential.

The workflows still trust GitHub account access, workflow configuration, hosted runners, action code and package/build inputs. A compromised account or signing runner can still misuse the updater key or produce malicious signed bytes. Artifact attestation binds bytes to GitHub's workflow/source claim but does not prove an honest, reproducible or vulnerability-free build. Goal 04I limits blast radius by denying release-write authority to the signing workflow and denying signing secrets, OIDC and attestation authority to draft/publication workflows. The publication `GITHUB_TOKEN` has only `actions: read` and `contents: write`; a separate credential with intended Repository Administration: read authority is exposed only to the immutable-settings preflight and is forbidden from Administration or Contents write authority. Enabling immutable releases remains a separate owner settings operation. Draft assets are re-downloaded and checked, publication fails unless the preflight reports enabled, the published Release must report `immutable=true`, and public bytes are rehashed without reusing the settings credential. `latest.json` itself is not signed, so a bad manifest can still deny update availability even though a substituted payload cannot pass Minisign verification. No HSM or isolated signing service exists.

The Windows NSIS artifact is updater-authenticated but not Authenticode-signed. Windows may report an unknown publisher; publication requires the exact version-bound owner decision `owner_accepts_unsigned_publisher_for_v<verified-version>`. Linux/macOS publication does not imply in-app installation, macOS notarization or Linux package signing. Goal 04I itself created no production candidate, tag, draft or Release; later owner-authorized release cycles published immutable `v0.1.1` and then `v0.1.2`, with `v0.1.2` current latest. See [production updater release runbook](../release/production-updater-release.md).

If the updater private key is compromised, an attacker who can also control update distribution could sign malicious updater artifacts accepted by applications trusting that key. Loss of the key prevents future signatures for that trust anchor. GitHub provenance does not replace updater signing; updater signing does not replace Windows Authenticode or macOS code signing/notarization. The committed public key and metadata SHA binding are not runtime cryptographic verification. Migration of already-installed applications to a different public key requires a separate security design; there is no fallback key, remote key fetch, key rollover or automatic trust-new-key behavior.

Goal 04D adds one explicit native HTTPS manifest read after a user clicks **Check for updates**. The endpoint is fixed in desktop configuration, and the Rust backend owns the 15-second timeout and disabled updater proxy. The renderer cannot supply a URL, headers, proxy, target or timeout and has no direct updater plugin permission. The check parses the manifest and applies Tauri's newer-version comparison; no automatic check or polling exists. HTTPS authenticates transport subject to normal TLS and GitHub account/distribution trust. The manifest response itself is not cryptographically signed, so compromise of the distribution endpoint can create a false announcement. The inherited plugin manifest fetch has no explicit NexusOps response-size cap and remains accepted debt in Goal 04E.

Goal 04E treats an announcement only as short-lived native authority. The exact retained URL must name the NexusOps GitHub release-download path, and redirects are limited to three across a fixed HTTPS GitHub asset-host allowlist. Proxies are disabled, connect and total timeouts are fixed at 10 and 300 seconds, and no retry occurs. Every accepted chunk is checked before append against the exact 128 MiB ceiling and streamed through Minisign verification using only the committed public key. The authenticated trusted comment is read only after successful cryptographic verification and must contain exactly one version corresponding to the announcement. Renderer-supplied transport/trust data, legacy unbounded verification, persistence, and automatic work are absent. Goal 04G grants installation only on supported Windows builds through a fresh opaque `VerifiedArtifactId`, exact NSIS URL basename, exclusive process quiescence, one-shot native consumption and cleanup-before-install. The builder fixes `restart_after_install(false)` and replaces the plugin default pre-exit cleanup hook because NexusOps performs its own ordered cleanup. Successful installer launch terminates the current process but does not prove installation or UAC success; no automatic relaunch exists. Linux and macOS expose no install action. A compromised production signing key plus distribution control could still produce an artifact the application accepts; updater verification does not establish code safety or OS code signing. Production `v0.1.2` is published, latest and immutable, and a manual Windows `0.1.1 → 0.1.2` acceptance exercised verified download, explicit installation, manual reopen, installed-byte identity and the subsequent no-update result. See [update architecture](../architecture/updates.md).

## Outside the current milestone

AI/plugin policy, recursive file operations and sync, binary editing, force overwrite or collaborative editing, certificate authorities, SSH agent forwarding, jump hosts, persistent or shared terminal sessions, vault export/recovery, hardware-backed keys, automatic updater installation/restart, OS-code-signed installers, telemetry, secure deletion of encrypted orphan records and an independent security audit. No compliance or complete resistance to local malware is claimed.
